# Leads → GoHighLevel Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A "Request information" form on every school page that stores the lead, rate-limits abuse in the database, forwards the lead to a GoHighLevel inbound webhook, and lists leads for admins at `/admin/leads`.

**Architecture:** Pure validation/payload/hash helpers in `src/lib/leads.ts`; a `SECURITY DEFINER` `submit_lead()` function owns inserts and rate limits (no API role can insert directly); one server action validates, hashes the IP, calls the RPC, then POSTs to GHL (failures logged only); admins read/update via RLS on `leads`.

**Tech Stack:** Next.js 16 Server Functions (`headers()`, `useActionState`), Supabase Postgres RPC + RLS, `node:crypto`, `node:test`.

**Spec:** `docs/superpowers/specs/2026-08-21-leads-ghl-design.md` — the SQL for the table, policies and `submit_lead()` is written there verbatim and is the source of truth for Task 2.

## Global Constraints

- Branch `feature/leads-ghl` is stacked on `feature/favorites-compare` (PR #5) because both edit the school-page hero; the PR targets that branch until #5 merges.
- Honeypot field name: `company_website`. Rate limits: 3 per hashed IP per hour, 1 per email+school per 24 h. Error code for user-safe SQL messages: `P0001`.
- Env: `GHL_WEBHOOK_URL` (server-only), `LEAD_IP_SALT` (optional). Never expose either with `NEXT_PUBLIC_`.
- Same token/primitive/test/SQL-patch rules as the favorites plan. Explicit `grant execute` on `submit_lead` is required (function defaults are revoked).
